SLICE 1 — Android sensor -> live sensor display
------------------------------------------------
Built SensorRepository, which reads live accelerometer + gyroscope at
~10 Hz on a background thread (never blocking the UI thread) and
publishes the latest sample of each plus the *observed* delivery rate
via a StateFlow. MainActivity renders this live on a Compose screen.
Added a JUnit4 unit test for the Hz calculation.

Installed on a real Samsung Galaxy S24 FE (SM-S721B, Android 16 / One
UI 8.5) connected over USB ADB. Live accel/gyro readout confirmed
working, observed rate ~12.5 Hz against the requested ~10 Hz.

SLICE 2 — Sensor -> orientation
---------------------------------
Added OrientationMath.kt: a pure-Kotlin quaternion -> azimuth/pitch/roll
conversion mirroring Android's own AOSP SensorManager algorithm exactly,
so it's unit-testable on the plain JVM and matches on-device output.
Registered the rotation-vector sensor in SensorRepository; MainActivity
now displays live azimuth/pitch/roll in degrees (radians internally,
converted only at the display boundary). One unit test caught a wrong
sign assumption before it ever reached the device (Android's azimuth is
clockwise-positive, not counterclockwise like a raw quaternion rotation).

Verified live orientation readout updating on the S24 FE.

SLICE 3 — Sensor -> baseline physics velocity/position
---------------------------------------------------------
Added a `dr/` package: WorldFrameAcceleration.kt (rotates raw device-
frame accel into WORLD frame using Slice 2's rotation matrix, then
removes gravity) and BaselinePhysicsIntegrator.kt (semi-implicit-Euler
double integration to a 2D East/North position + velocity). This is a
deliberately naive physics-only baseline (PRD Section 32's fallback
path) — no ZUPT, no bias correction, expected to drift, which is
intended, not a bug: it's the honest reference later ML must beat.
BaselineDeadReckoningRepository.kt is the coroutine glue wiring
SensorRepository's stream into the integrator. MainActivity shows the
live position/velocity with an on-screen caption warning it's a naive
baseline expected to drift.

Verified live position/velocity readout updating on the S24 FE.

SLICE 4 — GNSS outage detection
----------------------------------
Added a `gnss/` package: GnssFix.kt (raw fix data), GnssQuality.kt
(pure: is a fix good enough right now, by age + accuracy),
GnssOutageDetector.kt (pure: the GNSS_AIDED/TRANSITION/DEAD_RECKONING/
REACQUISITION hysteresis state machine per PRD Section 18, with proper
enter/exit dwell times so a single noisy sample can't flip the mode,
and every transition logged with its trigger condition).
LocationRepository.kt reads real GPS fixes via FusedLocationProviderClient
at ~1 Hz; GnssModeRepository.kt evaluates the detector on its own
independent 5 Hz clock (so GNSS detection keeps working even if the IMU
pipeline is down). MainActivity now requests location permission at
runtime and displays live GNSS mode/fix/last-transition.

BUG FOUND AND FIXED during on-device verification: the very first accel
sample of each run computed a multi-thousand-second "dt" against a 0L
sentinel instead of treating it as "no prior sample," which briefly sent
the DR position to ~1e11 meters immediately on launch. Root cause: a
different first-sample guard pattern than the one already used correctly
elsewhere in the codebase. Fixed with a nullable Long sentinel (makes the
bug class structurally impossible, not just patched). Retested, verified
via screenshot: position stayed small (sub-2m) at rest as expected.

Also hit and resolved an unrelated Windows/ADB driver glitch mid-session
(the ADB USB interface got stuck in a stale phantom state) — fixed by
restarting the ADB server and re-toggling USB debugging on the phone,
not a code issue.

Verified live GNSS mode readout on the S24 FE: correctly showed
DEAD_RECKONING (no fix available indoors) with the exact expected
trigger description logged.

SLICE 5 — Dead reckoning: state machine wiring + ZUPT + non-holonomic
constraint
--------------------------------------------------------------------
Added StationaryDetector.kt (pure, deterministic ZUPT trigger: sustained
low acceleration + gyro magnitude, same dwell/hysteresis principle as
the GNSS state machine — honestly documents that it can't distinguish
"at rest" from "coasting at constant velocity," an inherent limitation)
and NonHolonomicConstraint.kt (pure: vector-projects velocity onto
device heading, suppressing the sideways component — a simplified
WORLD-frame stand-in for PRD Section 20's vehicle-frame version, since
phone-to-vehicle alignment doesn't exist yet, with no "Turning" exemption
either since the ML motion classifier is Slice 6).

BaselinePhysicsIntegrator gained overrideVelocity() (sets velocity only,
leaves position untouched) as the mechanism both corrections use.
BaselineDeadReckoningRepository now also depends on GnssModeRepository:
applies ZUPT/NHC every tick, and resets the integrator every tick GNSS
mode is GNSS_AIDED, so the DR readout means "distance traveled since
GNSS was last good" (the actual drift-measurement quantity PRD wants),
not drift since app launch. This is the "state machine" wiring for this
slice: connecting Slice 4's previously-cosmetic mode to actually affect
the DR estimate (still no GNSS/DR position blending — that's Slice 7).

Verified with two screenshots ~15 seconds apart, phone at rest: position
stayed essentially at zero the whole time (not just at the first
reading), versus Slice 4's -0.85/-1.56 m drift over a similar period —
direct visible proof ZUPT is actually holding the estimate still.
The GNSS-mode-gated reset couldn't be visually confirmed indoors (no
real GPS lock reachable inside) — verified by code inspection + existing
unit tests instead, flagged for a direct outdoor check later.

PHASE 4 — Dataset inspection (IO-VNBD)
-----------------------------------------
Downloaded the IO-VNBD dataset (real research dataset: GPS + IMU
recordings from real vehicle drives across UK/France/Nigeria, from
github.com/onyekpeu/IO-VNBD — ~194 MB, stored via Git LFS). Verified
the download's checksum matched exactly before trusting it. Extracted
and inspected the actual CSV files plus the dataset's own descriptor
PDF (not just guessed from filenames).

Findings:
  - Confirmed real ~10 Hz smartphone sampling / 1 Hz GPS updates,
    matching our app's target rate.
  - IMPORTANT: found a real mismatch between how this dataset labels
    its accelerometer/gyroscope X/Y/Z axes and how Android's own raw
    sensors report X/Y/Z. Confirmed this by extracting and looking at
    the dataset's own diagram image (not by guessing) — their axes are
    relabeled/permuted relative to Android's standard convention. This
    matters: if we trained a model on this data's raw axes and fed it
    our own raw device readings without accounting for the mismatch,
    the model would get consistently wrong inputs. This has to be
    handled during feature extraction (Slice 6) — documented in
    docs/PROJECT_MAP.md so it isn't missed.
  - No pothole/turning/phone-moved labels exist per-moment in the data
    — only descriptions of what happened SOMEWHERE during each whole
    drive (e.g. "this 90-minute trip included some hard brakes and
    roundabouts"). Fine for training the velocity estimator (which has
    real GPS/speed ground truth throughout), not enough on its own for
    the motion classifier's pothole/phone-moved detection. Decision:
    use this dataset for velocity + "stationary" training (it even has
    dedicated 20+ minute stationary recordings, useful for tuning our
    own at-rest detector), and plan a short self-recorded session later
    specifically to capture potholes and phone-movement examples.
  - Confirmed the dataset's phone was mounted in a fixed, known
    orientation the whole time (windshield mount) — unlike our live app,
    which doesn't know how the phone is mounted. This is a second reason
    (beyond the axis-mismatch one above) our planned vehicle-frame
    conversion step is necessary, not optional.

Dataset is gitignored (confirmed via git check-ignore) — the ~194 MB
never risks landing in the repo. Re-download instructions recorded in
data/README.md for anyone who clones the repo fresh.

Two more real findings caught while building/running it:

     already learned early on. This matters for how the "time since

script's parsing logic.

ml/feature_extraction.py built — and a real sign-flip bug caught before
any model was trained
------------------------------------------------------------------------
Built the vehicle-frame feature extraction: converts raw phone-frame
accelerometer/gyro readings into "forward / lateral / up relative to
the car" using each moment's recorded gravity direction (since the
phone's mounting tilt isn't perfectly known, this is more robust than
assuming a single fixed angle).

Before trusting this for training, I checked it against reality: does
"forward acceleration" from this pipeline actually line up with the
car's real GPS speed changing? Across all 72 trips (nearly 14,000
real accelerate/decelerate events), it didn't — the data said pressing
the gas correlated with SLOWING DOWN, which is backwards. The
dataset's own diagram had suggested one axis direction was "forward,"
but the diagram turned out to not match the actual sign in the
recorded numbers. Flipped the axis, re-checked against the same real
data, and now it lines up correctly (accelerating correlates with
speeding up, as it should).

This is worth calling out because it's exactly the kind of bug that
could have silently trained a backwards model — one that predicts high
speed during braking and low speed during acceleration — and it might
not have been obvious until testing on a real drive much later. Caught
now because I checked the numbers against independent, real GPS speed
data before building anything on top of it, rather than trusting a
diagram or assuming the math was right just because it ran without
errors.

train_velocity_model.py — first real ML-vs-baseline result
---------------------------------------------------------------
Trained a Random Forest to predict forward speed from the windowed
sensor features, split by trip (not by row) so the same drive never
leaks between training and validation, and measured it against a
Python re-implementation of the app's own physics-only + ZUPT
baseline on the exact same held-out drives.

One deliberate exclusion: PRD wants "previous velocity" as a feature,
but since GPS updates only every ~9s in this data (see the earlier
finding), "previous row's GPS speed" is basically identical to the
current answer for 89 out of every 90 rows — including it would let
the model cheat by copying the answer instead of learning from the
IMU. Left it out for this pass.

Real result: the ML model's average error is 1.244 m/s, versus 5.205
m/s for the physics-only baseline — about 4x more accurate, and it won
on 13 of the 14 held-out drives. This is the first genuine, measured
proof in this project that machine learning actually helps here,
rather than being assumed to help because "AI/ML" is in the problem
title. One drive out of 14 the physics baseline actually won on — not
dug into yet, noted for later.

Honesty caveat worth keeping in mind: this measures how well the model
predicts speed tick-by-tick when given sensor readings, not yet how
well it holds up over several real minutes with zero GPS correction
(errors compound over time in ways a single-tick average doesn't
capture) — that fuller test comes later once everything is wired
together end-to-end.

Wired ML velocity into an actual position estimate — and found a real,
interesting limitation
------------------------------------------------------------------------
Picked option (a). Built a small piece of math that takes the model's
predicted speed each moment plus the direction we're facing and turns
that into an actual moving position (following the same approach the
original design document specifies). Wired it in alongside the
existing physics-based position, so both are now visible and directly
comparable on screen. Installed and ran it on the real phone — no
crashes, both positions displaying live.

Then, while just letting the phone sit on the desk to verify it stayed
stable, I noticed the physics-based position stayed almost perfectly
still (as expected) but the new ML-based position suddenly jumped by
about a meter and a half over less than a minute, then stopped moving
again. Dug into why: it's a real, honest design gap, not a bug. The
physics approach has "memory" — even if it briefly misreads a small
motion, that error only builds up a little before being corrected.
The new ML approach has none — every single moment it thinks the phone
might be moving, it applies the model's full speed estimate for that
instant, with no accumulated-error damping. So a brief nudge (probably
me bumping the desk while running commands) that the physics side
brushed off almost entirely caused a real jump in the ML-based
estimate.

I flagged this clearly rather than just working around it quietly, and
asked how to handle it. Decision: document it honestly now, and treat
the actual fix (there are a few reasonable options — a minimum-speed
cutoff, smoothing the model's output, or making the "are we stationary"
check stricter for this path) as a separate piece of work that deserves
proper thought rather than a rushed patch. This is exactly the kind of
thing that only shows up from testing on real hardware with real
sensor noise — all the automated tests still pass, because they
correctly verify the math does what it was built to do; they just
can't reveal that the design itself has this consequence in the real
world.
